## Act 1 · Hook & Problem

### 01 · ปัญหา: คนทำไม่ได้เงิน (s1: DooToon)

สวัสดีครับ ผม นวพล โพธิ์แหบ รหัสประจำตัวนักศึกษา 66050221 ขอแนะนำโปรเจกต์ DOOTOON (ดูตูน) ครับ

ทุกวันนี้มังงะและนิยายแปลไทยโดนดูดไปลงเว็บเถื่อนเต็มไปหมด คนแปลกับคนวาดไม่ได้เงินสักบาท ส่วนเว็บที่มีอยู่ก็มีปัญหา — ถ้าตอนไหนโดนแจ้งลบลิขสิทธิ์ เงินที่เก็บจากคนซื้อมาแล้วมักจะค้าง คืนเงินไม่ได้ คนซื้อโวย คนทำเสียขวัญ

DOOTOON คือเว็บอ่านมังงะและนิยายภาษาไทยที่ออกแบบมาเพื่อแก้ปัญหานี้ — หนึ่ง ทำให้คนจ่ายเงินถึงคนทำจริง สอง ถ้าตอนไหนโดนลบ ระบบจะย้อนเงินคืนคนซื้อทุกคนอัตโนมัติ รันอยู่จริงบน Multi-Cloud ด้วย Azure AKS, Cloudflare R2 และ Stripe ครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Multi-Cloud Architecture**
>   - *คืออะไร:* สถาปัตยกรรมที่กระจายงานข้ามคลาวด์หลายผู้ให้บริการ ไม่ผูกขาดกับเจ้าใดเจ้าหนึ่ง
>   - *ในโปรเจกต์เรา:* รวม Azure (AKS + Database), Cloudflare (DNS/WAF + R2 Storage) และ Stripe (ระบบชำระเงิน) เพื่อดึงจุดเด่นของแต่ละเจ้าและลดต้นทุนสูงสุด
> - **AKS (Azure Kubernetes Service)**
>   - *คืออะไร:* บริการ Managed Kubernetes บน Microsoft Azure ช่วยจัดการคอนเทนเนอร์แบบอัตโนมัติ
>   - *ในโปรเจกต์เรา:* รัน Go Microservices ทั้ง 9 ตัว และ Next.js คอยดูแล Health Check, Auto-restart เมื่อพัง และกระจายโหลด
> - **R2 (Cloudflare R2 Storage)**
>   - *คืออะไร:* พื้นที่เก็บไฟล์แบบ Object Storage ของ Cloudflare ที่รองรับมาตรฐาน S3 API
>   - *ในโปรเจกต์เรา:* ใช้เก็บไฟล์ภาพหน้ามังงะ `.webp` ทั้งหมด โดยมีจุดเด่นสำคัญที่สุดคือ **ค่า Egress Fee เป็น $0/GB**
> - **Stripe**
>   - *คืออะไร:* แพลตฟอร์มรับชำระเงินระดับโลกที่ได้มาตรฐาน PCI-DSS Level 1
>   - *ในโปรเจกต์เรา:* ใช้ตัดเงินบาท (THB) ผ่านทั้งบัตรเครดิต/เดบิต และระบบ QR พร้อมเพย์ โดยเว็บไม่ต้องเสี่ยงเก็บข้อมูลบัตรเอง

### 02 · ผู้ใช้ 3 กลุ่ม ใช้เว็บเดียวกัน (s1b: Users)

ระบบนี้มีผู้ใช้งาน 3 กลุ่มหลักบนเว็บเดียวกันครับ:

1. **Readers (คนอ่าน)**: เข้ามาเปิดอ่าน 3 ตอนแรกและตอนล่าสุดได้ฟรีทันทีโดยไม่ต้องสมัครสมาชิก หากต้องการอ่านตอนอื่นสามารถเติมเหรียญผ่าน PromptPay หรือบัตรเครดิตด้วย Stripe
2. **Creators & Illustrators (ทีมนักเขียนและผู้วาดภาพประกอบ)**: ในวงการการ์ตูน คนที่เหนื่อยที่สุดคือ Illustrator ที่ต้องวาดภาพสัปดาห์ละหลายสิบหน้า แพลตฟอร์มของเราจึงมีระบบ Creator Splits ตั้งราคาขายและกำหนดสัดส่วนรายได้ของทีมไว้ล่วงหน้า (เช่น นักเขียน/ผู้แปล 70%, Illustrator 30%) เงินสดส่วนแบ่งจะถูกโอนตรงเข้ากระเป๋าของ Illustrator แยกอิสระทันทีตอนมีคนซื้อ
3. **Platform / Admin**: หน้าจัดการหลังบ้าน หากตอนไหนมีปัญหาลิขสิทธิ์ แอดมินกด Takedown ได้ทันที ระบบจะสั่งซ่อนตอน บล็อกไฟล์รูป และคืนเหรียญให้คนซื้อทุกคนอัตโนมัติ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **RBAC (Role-Based Access Control)**
>   - *คืออะไร:* ระบบควบคุมสิทธิ์การเข้าถึงข้อมูลตามบทบาทหน้าที่ของผู้ใช้
>   - *ในโปรเจกต์เรา:* แบ่งเป็น 3 roles ชัดเจนคือ `reader`, `creator`, และ `moderator/admin` เช็กสิทธิ์ตั้งแต่หน้าบ้าน Next.js จนถึงด่านใน Go microservices
> - **PromptPay**
>   - *คืออะไร:* โครงสร้างพื้นฐานการชำระเงินอิเล็กทรอนิกส์ของไทยผ่านเลขบัตรประชาชน/เบอร์โทรศัพท์ หรือ QR Code
>   - *ในโปรเจกต์เรา:* ให้คนอ่านสแกนจ่ายเงินบาทผ่าน Stripe ด้วยค่าธรรมเนียมเพียง 1.65% ไม่มีค่าธรรมเนียมขั้นต่ำ เหมาะกับยอดจ่ายขนาดเล็ก (Micro-transactions)

### 02b · เป้าหมายหลักและขอบเขตในโครงการ (s1c: Scope)

เป้าหมายและขอบเขตของโครงการแบ่งออกเป็น 2 ฝั่งชัดเจนครับ:

**ฝั่งเป้าหมายหลัก (Core Goals)**:
1. พิสูจน์วงจรเงินจริงครบ Loop (End-to-End) ตั้งแต่อ่านฟรี เติมเงิน ซื้อตอน แบ่งรายได้ 30/70 ไปจนถึง Takedown แล้วคืนเงินอัตโนมัติ
2. สถาปัตยกรรม 9 Go Microservices ไร้สถานะ (Stateless) บน Azure AKS แยก 6 Schemas บน PostgreSQL 16
3. มีระบบ CI/CD บน Azure DevOps ปล่อยขึ้นเซิร์ฟเวอร์แบบ Zero-Downtime พร้อมด่านตรวจ Coverage ≥ 80%
4. มีหน้ากระดาน Observability Dashboard (OTel + OpenObserve) ดู Logs, Traces, Metrics ได้ครบถ้วน
5. บริหารงบประมาณแบบ Lean FinOps ให้อยู่ในงบนักศึกษา ($17–23/เดือน) โดยตัดค่า Egress มหาศาลด้วย Cloudflare R2

**ฝั่งขอบเขต (In-Scope vs Out-of-Scope)**:
- **สิ่งที่ทำในโครงการ (In-Scope)**: หน้าเว็บ Next.js 16 (BFF) + 9 Go Microservices, สมุดบัญชี Append-Only Ledger ที่ตัดเงินด้วย ACID Transaction, ลิงก์รูปภาพ HMAC Signed URL หมดอายุ 15 นาที, ระบบ Takedown คืนเงิน 100%
- **สิ่งที่เราตั้งใจไม่ทำในเฟสนี้ (Non-Goals เพื่อรักษาความสมจริงของ Scope)**:
  - ไม่ทำ AI ตรวจจับภาพลิขสิทธิ์ล่วงหน้า (เพราะเปลืองทรัพยากร และเลือกใช้สัญญาพร้อมระบบ Takedown + Refund อัตโนมัติแทน)
  - ไม่ทำ Native Mobile App (เน้นทำ Responsive Web ให้ดีบนทุกอุปกรณ์ก่อน)
  - ไม่ทำ Unlimited Subscription (เพราะโมเดลอ่านบุฟเฟต์จะทำให้การคิดเงินส่วนแบ่งรายตอนของครีเอเตอร์เสียสมดุล)

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **End-to-End Scope**
>   - *คืออะไร:* ขอบเขตการทำงานที่ครอบคลุมตั้งแต่ต้นน้ำจนถึงปลายน้ำโดยไม่มีจุดขาดตอน
>   - *ในโปรเจกต์เรา:* ระบบไม่ได้จบแค่หน้าเว็บสวยงาม แต่มีระบบเงินจริง, ฐานข้อมูลจริง, การแบ่งรายได้ตามสัญญา, และการจัดการข้อพิพาทลิขสิทธิ์ครบวงจร
> - **Non-Goals / Scope Boundaries**
>   - *คืออะไร:* สิ่งที่ทีมกำหนดไว้อย่างชัดเจนว่าจะ "ไม่ทำ" เพื่อป้องกัน Scope Creep
>   - *ในโปรเจกต์เรา:* การระบุว่าไม่ทำ AI Pre-screen หรือ Unlimited Subscription แสดงถึงการเข้าใจข้อจำกัดทางวิศวกรรมจริงและโมเดลธุรกิจที่ซื่อสัตย์ต่อครีเอเตอร์
### 03 · End-to-end flow 7 ขั้นตอน (s2: Flow)

โฟลวทั้งระบบสรุป 7 ขั้นตอนการทำงานจริงจากซ้ายไปขวาครับ:

เริ่มจาก Guest เข้ามาอ่านฟรี > เมื่อถูกใจก็สมัครสมาชิกผ่านระบบ Better-Auth > เติมเหรียญ 100 coin ผ่าน Stripe ที่มีระบบกันเติมเบิ้ล > กดซื้อตอน 40 coin เงินจะถูกหักและแบ่งให้ครีเอเตอร์ทันที > เข้าอ่านได้ปกติ > และหากเกิดเคส Takedown ระบบจะซ่อนตอน และย้อนคืนเหรียญให้คนซื้อทุกคน 100% เต็มทันทีครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Better-Auth**
>   - *คืออะไร:* ไลบรารี Authentication สมัยใหม่สำหรับ Next.js และ TypeScript
>   - *ในโปรเจกต์เรา:* ดูแลระบบสมัครสมาชิก, ล็อกอิน Email/Password และ Google OAuth พร้อมออก Session Cookie แบบปลอดภัย
> - **End-to-End Flow**
>   - *คืออะไร:* วงจรการทำงานตั้งแต่จุดเริ่มต้นของผู้ใช้คนแรก ไปจนถึงปลายทางสุดท้ายของระบบ
>   - *ในโปรเจกต์เรา:* ครอบคลุม 7 ขั้นตอน: อ่านฟรี → สมัคร → เติมเงิน → ซื้อตอน → ปลดล็อกอ่าน → ตรวจสอบลิขสิทธิ์ → คืนเงินอัตโนมัติ

### 04 · Constraints โจทย์ 3 ข้อที่กำหนดระบบ (s3: Constraints)

ก่อนจะสร้างสถาปัตยกรรม เราตั้งโจทย์จำกัดไว้ 3 ข้อที่กำหนดหน้าตาระบบทั้งหมด:

1. **เงินต้องถูกต้อง (ACID)**: การหักเหรียญ, ให้สิทธิ์อ่าน, และแบ่งรายได้ครีเอเตอร์ ต้องสำเร็จพร้อมกันใน Transaction เดียว หากล้มเหลวต้อง Rollback ทั้งหมด ห้ามมีสถานะเงินหาย
2. **รูปคือ 95% ของทราฟฟิก**: ไฟล์ภาพห้ามวิ่งผ่านเซิร์ฟเวอร์บน Azure เพื่อเลี่ยงค่า Bandwidth Egress มหาศาล จึงแยกไปเสิร์ฟผ่าน Cloudflare R2 ที่ Egress ฟรี ($0)
3. **งบนักศึกษา (~$20/เดือน)**: คุมค่าใช้จ่ายให้อยู่ในเครดิต Azure (~$17-23/เดือน) โดยตัดทรัพยากรราคาแพงอย่าง NAT Gateway, Bastion, และ Redis ออกทั้งหมด

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **ACID Transaction**
>   - *คืออะไร:* มาตรฐานความถูกต้องระดับสูงสุดของฐานข้อมูล (Atomicity, Consistency, Isolation, Durability)
>   - *ในโปรเจกต์เรา:* ใช้กับระบบเงินใน PostgreSQL — ตอนซื้อตอน การหักเหรียญคนซื้อ, ให้สิทธิ์อ่าน, และแบ่งเปอร์เซ็นต์ให้คนวาด/คนแปล ต้องสำเร็จพร้อมกันทั้ง 3 อย่าง หากเน็ตหลุดหรือระบบล่มกลางคัน ฐานข้อมูลจะยกเลิก (Rollback) กลับคืนสภาพเดิม 100% เงินไม่มียอดค้างเติ่ง
> - **Egress Fee**
>   - *คืออะไร:* ค่าธรรมเนียมถ่ายโอนข้อมูลออกจากคลาวด์ลงสู่อินเทอร์เน็ตภายนอก (Data Egress)
>   - *ในโปรเจกต์เรา:* Azure คิดค่า Bandwidth ขาออก ~$0.087/GB ซึ่งแพงมากสำหรับเว็บการ์ตูน เราจึงแยกไฟล์รูปไปไว้บน Cloudflare R2 ที่มีนโยบาย **Zero-Egress Fee ($0/GB)** ทำให้ประหยัดงบได้มหาศาล
> - **NAT Gateway (Network Address Translation Gateway)**
>   - *คืออะไร:* อุปกรณ์เครือข่ายของคลาวด์ที่ช่วยให้เครื่องใน Private Subnet สามารถออกสู่อินเทอร์เน็ตได้
>   - *ในโปรเจกต์เรา:* Azure คิดเงินค่า NAT Gateway ราว ~$32/เดือน เราตัดทิ้งและออกแบบให้คลัสเตอร์ไม่ต้องพึ่งพามัน ช่วยประหยัดเงินในงบนักศึกษา
> - **Bastion Host**
>   - *คืออะไร:* เซิร์ฟเวอร์ทางผ่านพิเศษสำหรับกระโดด (Jump host) เข้าไปจัดการเครื่องใน Private Network
>   - *ในโปรเจกต์เรา:* ตัดออกเพื่อประหยัดเงิน ~$35/เดือน แล้วใช้คำสั่ง `kubectl port-forward` เชื่อมต่อเข้าคลัสเตอร์โดยตรงผ่าน Identity ปลอดภัย

## Act 2 · Cloud Architecture (Big Picture)

### 05 · Full Cloud Architecture ภาพรวมทั้งระบบ (s4: Full Arch)

ภาพรวมสถาปัตยกรรม Multi-Cloud ในหน้าเดียวครับ:

ฝั่งซ้ายคือผู้ใช้และ Stripe วิ่งผ่านด่านหน้า Cloudflare Edge ที่คุม DNS, DDoS, WAF และแคชรูปภาพ จากนั้นทราฟฟิกจะวิ่งเข้าระบบหลังบ้านบน Azure VNet ผ่าน Envoy Gateway บน AKS ซึ่งข้างในมี Next.js และ Go Microservices 9 ตัว ทำงานร่วมกับ PostgreSQL 16 Flexible Server แบบ Private Subnet ไม่มี Public IP และฝั่งขวาคือ Cloudflare R2 สำหรับเก็บภาพมังงะโดยเฉพาะ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **DNS (Domain Name System)**
>   - *คืออะไร:* สมุดโทรศัพท์ของอินเทอร์เน็ต แปลงชื่อภาษาคน `dootoon.store` ให้เป็นหมายเลข IP Address ของเซิร์ฟเวอร์
>   - *ในโปรเจกต์เรา:* จัดการโดย Cloudflare ซึ่งมีความเร็วในการ Lookup ต่ำระดับเสี้ยววินาที และเปลี่ยน IP หลังบ้านได้ทันทีโดยไม่ต้องรอเป็นชั่วโมง
> - **WAF (Web Application Firewall)**
>   - *คืออะไร:* กำแพงไฟตรวจจับและกรองคำสั่งอันตรายก่อนถึงเซิร์ฟเวอร์
>   - *ในโปรเจกต์เรา:* ดักจับการโจมตีประเภท SQL Injection, Cross-Site Scripting (XSS), และบอทที่พยายามสุ่มยิงสแกนช่องโหว่ของคลัสเตอร์ AKS
> - **DDoS Protection (Distributed Denial of Service)**
>   - *คืออะไร:* ระบบป้องกันการยิงถล่มด้วยปริมาณทราฟฟิกมหาศาลจากคอมพิวเตอร์ผี (Botnet) เพื่อทำให้เว็บล่ม
>   - *ในโปรเจกต์เรา:* Cloudflare ซับแรงกระแทกระดับ Terabit/s ที่ Edge ทันที ทราฟฟิกยิงถล่มจะไม่มีทางหลุดเข้ามาถึงเครื่อง Azure AKS ของเรา
> - **แคชรูปภาพ (CDN Edge Caching)**
>   - *คืออะไร:* **ไม่ใช่การเลือก 10 อันดับมังงะยอดนิยมมาแคชล่วงหน้า** แต่คือการทำ **HTTP Cache ที่โหนด Edge ใกล้บ้านผู้ใช้โดยอัตโนมัติ**
>   - *ในโปรเจกต์เรา:* เมื่อมีผู้ใช้เปิดดูรูปตอนมังงะหน้าใดหน้าหนึ่ง Worker จะส่ง Header `cache-control: public, max-age=3600` ทำให้รูปถูกบันทึกสำเนาไว้ที่ Edge ของ Cloudflare ในไทยนาน 1 ชั่วโมง คนถัดไปเปิดดูจะโหลดได้ทันที 0ms ไม่ต้องยิงขอจาก R2 ซ้ำ
> - **Azure VNet (Virtual Network)**
>   - *คืออะไร:* เครือข่ายเสมือนส่วนตัวบน Azure ที่ตัดขาดจากอินเทอร์เน็ตภายนอก
>   - *ในโปรเจกต์เรา:* วางวง IP `10.42.0.0/16` แล้วแบ่งเป็น 2 ซอย (Subnets) แยกกันชัดเจน คือซอยประมวลผล (AKS) และซอยฐานข้อมูล (Database)
> - **Delegated Subnet**
>   - *คืออะไร:* ซับเน็ตเฉพาะที่มอบอำนาจให้เซอร์วิสของ Azure บริหารจัดการเอง
>   - *ในโปรเจกต์เรา:* ซอย `snet-db (10.42.1.0/24)` มอบให้ PostgreSQL Flexible Server เท่านั้น เซอร์วิสอื่นห้ามเข้ามาปน ทำให้ฐานข้อมูลไม่มี Public IP ปลอดภัยสูงสุด

### 06 · Traffic routing 4 เส้นทาง (s6: Traffic routing)

ทราฟฟิกวิ่งเข้า Cloud แยกออกเป็น 4 เส้นทางตามหน้าที่ชัดเจนครับ:

1. **`dootoon.store` → `web:3000`**: หน้าเว็บหลัก Next.js SSR + BFF สำหรับคนอ่านและครีเอเตอร์
2. **`api.dootoon.store` → `gateway:8080`**: สำหรับยิง Public API ตรง และเป็นเส้นทางที่ใช้ทดสอบโหลด k6 ยิงเข้า reader pod
3. **`obs.dootoon.store` → `OpenObserve:5080`**: ให้ DevOps เปิดดูหน้า Dashboard สำหรับมอนิเตอร์ Logs, Traces และ Metrics
4. **`img.dootoon.store` → `Cloudflare R2`**: เส้นทางดาวน์โหลดรูปมังงะโดยตรง โดยมี Worker ตรวจสอบลายเซ็น HMAC ไม่ผ่าน Go หรือ AKS เลย

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Full Strict TLS (Transport Layer Security)**
>   - *คืออะไร:* การเข้ารหัส HTTPS แบบหัวจรดท้าย (End-to-End Encryption)
>   - *ในโปรเจกต์เรา:* จาก Browser 🔒(HTTPS) → Cloudflare 🔒(HTTPS) → Envoy Gateway บน AKS โดยใช้ใบรับรองความปลอดภัยที่ถูกต้องแท้จริงทั้งสองฝั่ง ข้อมูลไม่มีการหลุดเป็น Plaintext เลย
> - **Envoy Gateway (Kubernetes Gateway API)**
>   - *คืออะไร:* ประตูรับทราฟฟิกเข้าคลัสเตอร์มาตรฐานใหม่ของ Kubernetes มาแทนที่ Ingress คอนโทรลเลอร์เดิม
>   - *ในโปรเจกต์เรา:* ทำหน้าที่ผูกใบรับรอง TLS จาก Let's Encrypt และกระจายทราฟฟิกตาม Hostname ไปยัง Service `web:3000`, `gateway:8080`, หรือ `openobserve:5080`
> - **HMAC Token (Hash-based Message Authentication Code)**
>   - *คืออะไร:* ลายเซ็นดิจิทัลที่สร้างจาก Secret Key ที่รู้กันเฉพาะเซิร์ฟเวอร์หลังบ้านกับ Cloudflare Worker
>   - *ในโปรเจกต์เรา:* เวลาคนอ่านได้รับสิทธิ์ดูตอน Go จะสร้าง URL รูปที่มี `?exp=เวลาหมดอายุ&token=ลายเซ็น` เพื่อกันไม่ให้คนแอบก็อปลิงก์รูปไปแชร์ให้คนอื่นดูด เพราะถ้าไม่มี Secret Key จะปลอมลายเซ็นไม่ได้ และทุกลิงก์จะหมดอายุภายใน 15 นาที
> - **Cloudflare Worker**
>   - *คืออะไร:* เซิร์ฟเวอร์เลสโค้ด (JavaScript) ที่รันกระจายอยู่ทั่วโลกบน Edge Network ของ Cloudflare
>   - *ในโปรเจกต์เรา:* คอยเฝ้าดักหน้าโดเมน `img.dootoon.store` แกะตรวจ HMAC Token ก่อนเปิดประตูให้ดึงไฟล์จาก R2 Bucket

### 07 · Inside web:3000 (s7: BFF Pattern)

ฝั่งเว็บใช้สถาปัตยกรรม Backend-for-Frontend (BFF) ครับ:

เบราว์เซอร์จะไม่คุยกับ Go ตรงๆ แต่จะยิงมาที่ `/api/*` ของ Next.js บนโดเมนเดียวกัน (Same-Origin) ทำให้หน้าบ้านไม่เห็น URL หรือ Secrets หลังบ้าน จากนั้น Next.js ฝั่ง Server จะประสานงานเรียก Go Microservices ในคลัสเตอร์ พร้อมแนบ Header ยืนยันตัวตน `X-User-ID` และ `X-User-Role` ไปด้วยครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **BFF (Backend-for-Frontend)**
>   - *คืออะไร:* สถาปัตยกรรมที่ทำ "หลังบ้านเฉพาะสำหรับหน้าเว็บ"
>   - *ในโปรเจกต์เรา:* คือโค้ดส่วน `web:3000` (Next.js `/api/*`) ที่ทำหน้าที่เป็นตัวกลาง หน้าเว็บไม่ต้องติดต่อ Go ตรงๆ แต่ให้ Next.js ฝั่ง Server ไปรวบรวมข้อมูลจาก Go หลายๆ service มาจัดรูปแบบให้พอดีกับหน้าจอในรอบเดียว
> - **SSR (Server-Side Rendering)**
>   - *คืออะไร:* การประมวลผลเรนเดอร์หน้า HTML บนเซิร์ฟเวอร์ก่อนส่งกลับไปที่เบราว์เซอร์
>   - *ในโปรเจกต์เรา:* ใช้กับหน้าแคตตาล็อกและรายละเอียดเรื่อง เพื่อให้ Search Engine (SEO) เก็บข้อมูลได้ง่าย และผู้ใช้เปิดหน้าแรกได้เร็ว
> - **Same-Origin Policy**
>   - *คืออะไร:* นโยบายความปลอดภัยของเบราว์เซอร์ที่จำกัดการร้องขอข้ามโดเมน
>   - *ในโปรเจกต์เรา:* เบราว์เซอร์ยิงหา `/api/*` บนโดเมนเดียวกัน ไม่ต้องเปิดสิทธิ์ CORS ข้ามเครื่อง ช่วยลดความเสี่ยงจากการโดนขโมย Token

### 08 · Inside AKS: Go 9 Microservices (s8: Microservices)

บน Kubernetes เราแยกการทำงานออกเป็น 9 Go Microservices ชัดเจน:

* `identity:8081` — ระบบผู้ใช้, ล็อกอิน, บทบาท (Roles), จัดการแบน
* `catalog:8082` — ข้อมูลเรื่อง, ตอน, ราคา, ส่วนแบ่งทีมนักเขียน (% splits)
* `commerce:8083` — หัวใจการเงิน คุมสมุดบัญชี Ledger, ตัดเหรียญ, แบ่งรายได้ (ACID)
* `reader:8084` — ตรวจสิทธิ์อ่าน (ถาม 3 เจ้า) + เซ็น HMAC URL (มี HPA 1➔4 pods)
* `moderation:8085` — ระบบ Takedown แจ้งลบตอน, สั่งลบรูป, ย้อนเงินคืนอัตโนมัติ
* `community:8086` — คอมเมนต์, ตรวจคำห้าม, คอมเมนต์ติดเหรียญ
* `library:8087` — ตำแหน่งหน้าที่อ่านค้างไว้, ติดตามเรื่อง
* `media:8088` — รับรูป, แปลงเป็น WebP, ส่งขึ้น Cloudflare R2
* `gateway:8080` — ประตูรับ API ภายนอก ส่งต่อไปยัง reader

ทุกตัวเป็น Stateless REST พร้อมระบบ Health check และ OpenTelemetry Trace ทั้งหมดครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Stateless REST**
>   - *คืออะไร:* บริการที่ไม่มีการจำสถานะ (Session) ค้างไว้ในหน่วยความจำเครื่อง
>   - *ในโปรเจกต์เรา:* ทุก Request ถือข้อมูลครบในตัว หากเซอร์วิสใดพังหรือ Pod ดับ Kubernetes สามารถเปิดตัวใหม่มาแทนที่ได้ทันทีโดยที่ผู้ใช้ไม่รู้สึก
> - **OTel (OpenTelemetry) Trace**
>   - *คืออะไร:* มาตรฐานกลางในการเก็บและติดตามเส้นทางการเดินทางของ Request ข้าม Microservices
>   - *ในโปรเจกต์เรา:* เมื่อมี Request ยิงเข้ามา Gateway จะแปะ Trace ID และส่งต่อข้ามเซอร์วิส ทำให้เห็นแผนผังได้ชัดเจนว่าจุดไหนทำงานช้าหรือเกิด Error
> - **Health Checks (`/healthz`, `/readyz`)**
>   - *คืออะไร:* API จุดตรวจสุขภาพของแอปพลิเคชัน
>   - *ในโปรเจกต์เรา:* `healthz` เช็กว่าโปรแกรมยังไม่แฮงก์ (Liveness) ส่วน `readyz` เช็กว่าต่อฐานข้อมูลติดพร้อมรับงานหรือยัง (Readiness)

### 09 · Money In: Top-Up Flow (s9: Stripe Top-Up)

การเติมเหรียญแบ่งเป็น 2 ขา:

ขาเติมเงิน ผู้ใช้เลือกแพ็กเกจ BFF จะสร้าง Stripe Checkout Session เมื่อจ่ายสำเร็จ Stripe Webhook จะยิงกลับมาที่ระบบเพื่อตรวจสอบลายเซ็น จากนั้นสั่งให้ `commerce:8083` บันทึกเหรียญลง Ledger พร้อม Idempotency Key ป้องกันการเติมซ้ำ และมีหน้า `/verify` เป็นทางสำรองหาก Webhook ตกหล่น

ส่วนขาเปิดอ่าน ReaderPage จะยิงตรวจสอบผ่าน Catalog และ Gateway ไปยัง Reader เพื่อเช็กสิทธิ์ก่อนปล่อยเนื้อหาครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Stripe Checkout Session**
>   - *คืออะไร:* หน้าต่างรับชำระเงินสำเร็จรูปที่โฮสต์บนเซิร์ฟเวอร์ที่ปลอดภัยของ Stripe
>   - *ในโปรเจกต์เรา:* ระบบส่งยอดเงินเป็น "สตางค์" (เช่น 100 บาท ส่ง 10000 สตางค์) พร้อมแนบ User ID เข้าไปใน Metadata เพื่อให้ดึงกลับมาเติมเหรียญถูกคน
> - **Webhook & Signature Verification**
>   - *คืออะไร:* กลไกที่ระบบภายนอก (Stripe) ยิง HTTP POST กลับมาแจ้งเตือนเซิร์ฟเวอร์เราอัตโนมัติเมื่อลูกค้าจ่ายเงินเสร็จ
>   - *ในโปรเจกต์เรา:* Next.js ต้องนำ Secret Key มาถอดรหัสตรวจสอบ Header ลายเซ็นก่อนเสมอ เพื่อป้องกันคนร้ายยิงปลอมคำสั่งว่าจ่ายเงินแล้ว
> - **Idempotency Key**
>   - *คืออะไร:* กุญแจรหัสเฉพาะสำหรับคำสั่งธุรกรรมการเงิน เพื่อการันตีว่าคำสั่งที่ส่งมาซ้ำจะถูกประมวลผลแค่ครั้งเดียว
>   - *ในโปรเจกต์เรา:* ตั้งชื่อคีย์ตาม Stripe Session ID เช่น `stripe_sess_123` หาก Webhook ยิงซ้ำ ระบบจะส่งผลสำเร็จเดิมกลับไป แต่ไม่บวกเหรียญซ้ำเด็ดขาด

### 10 · Purchase: 5 ขั้นใน 1 Transaction (s10: Purchase)

หัวใจของความถูกต้องทางการเงินคือการซื้อตอน 1 ครั้ง จะต้องเกิด 5 ขั้นตอนใน 1 Database Transaction เสมอ:

1. ล็อกแถวผู้ใช้เพื่อป้องกัน Race Condition
2. ตรวจสอบ Idempotency Key ป้องกันการกดซื้อซ้ำ
3. หักเหรียญโบนัสก่อนเหรียญจริง
4. บันทึกสิทธิ์การเข้าถึง (Entitlement)
5. แบ่งรายได้ 30% ให้แพลตฟอร์ม และ 70% ให้ทีมงาน โดยแบ่งจ่ายตรงเข้ากระเป๋าของ Author (นักเขียน/ผู้แปล 70%) และ **Illustrator (ผู้วาดภาพประกอบ 30%)** แยกอิสระทันที

หากขั้นตอนใดขั้นตอนหนึ่งพัง ระบบจะ Rollback ทั้งหมด เงินจะไม่สูญหายครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Race Condition & Row Locking (`SELECT ... FOR UPDATE`)**
>   - *คืออะไร:* ภาวะแย่งชิงทรัพยากรเมื่อมีสองคำสั่งพยายามแก้ยอดเงินพร้อมกันในเวลาเสี้ยววินาที
>   - *ในโปรเจกต์เรา:* ใช้คำสั่ง SQL `FOR UPDATE` ล็อกแถวผู้ใช้คนนั้นไว้ใน Transaction คำสั่งที่สองจะต้องรอจนกว่าคำสั่งแรกจะเสร็จ ป้องกันเหรียญติดลบ
> - **Bonus-First Debit**
>   - *คืออะไร:* ตรรกะการหักเหรียญโบนัส/เหรียญฟรีก่อนเหรียญจริงที่เติมเงินเข้ามา
>   - *ในโปรเจกต์เรา:* ออกแบบเพื่อปกป้องสิทธิ์ผู้ใช้และครีเอเตอร์ เพราะเหรียญโบนัสจะไม่ถูกนำไปคำนวณแบ่งส่วนแบ่งเงินจริงให้แก่ทีมครีเอเตอร์
> - **Entitlement**
>   - *คืออะไร:* สิทธิ์การครอบครองเนื้อหาที่ผู้ใช้ได้รับอย่างเป็นทางการ
>   - *ในโปรเจกต์เรา:* บันทึกในตาราง `commerce.entitlements` เพื่อยืนยันว่า User คนนี้มีสิทธิ์เปิดอ่านตอน Chapter นี้ได้ตลอดไป
> - **Creator Splits for Illustrators**
>   - *คืออะไร:* ระบบกระจายรายได้อัตโนมัติให้แก่ทีมสร้างสรรค์มังงะหลายคนตามสัดส่วน
>   - *ในโปรเจกต์เรา:* ปกติ Illustrator มักเป็นผู้เสียเปรียบในระบบเดิม ระบบนี้จึงการันตีเงินส่วนแบ่งเข้ากระเป๋าของ Illustrator โดยตรงแบบ Realtime ในทุกๆ การกดซื้อตอน

### 11 · Gates + Takedown (s11: Gates & Takedown)

ระบบความปลอดภัยมี 2 ด้าน:

ฝั่ง **Read Gates**: ก่อนเปิดอ่าน `reader` จะไล่ตรวจสิทธิ์ — ตอนนี้ถูกลบไหม, เป็นตอนฟรีหรือไม่, เป็นแอดมินหรือทีมงานไหม, หรือเคยซื้อหรือยัง หากผ่านจะออก HMAC Token ที่มีอายุ 15 นาทีให้ไปโหลดรูป

ฝั่ง **Takedown**: เมื่อแอดมินสั่งลบ ระบบจะซ่อนตอน, สั่งลบรูปบน R2, วนคืนเงินให้คนซื้อทุกคน 100% และบันทึก Audit log ทันทีครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Read Gate Hierarchy**
>   - *คืออะไร:* ลำดับขั้นการตรวจสอบสิทธิ์จากจุดที่ต้นทุนต่ำสุดไปยังจุดที่ต้นทุนสูงสุด
>   - *ในโปรเจกต์เรา:* ตรวจสอบตามลำดับ: โดนลบไหม? → เป็นตอนฟรีไหม? → เป็น Admin/Creator ไหม? → ถ้าไม่ใช่จึงวิ่งไปค้นฐานข้อมูล Commerce เพื่อประหยัด CPU ฐานข้อมูล
> - **Takedown Cascade**
>   - *คืออะไร:* การลบเนื้อหาแบบลูกโซ่ที่แผ่ผลกระทบไปทั้งระบบเพื่อแก้ปัญหาลิขสิทธิ์
>   - *ในโปรเจกต์เรา:* ซ่อนตอนทันที → สั่งลบไฟล์ภาพจริงใน Cloudflare R2 → วนคืนเหรียญให้คนซื้อทุกคน 100% ผ่านสมุดบัญชี → บันทึก Audit Log เพื่อป้องกันคดีความลิขสิทธิ์ตกค้าง
> - **Audit Log**
>   - *คืออะไร:* บันทึกประวัติการกระทำสำคัญของระบบแบบห้ามแก้ไข (Immutable History)
>   - *ในโปรเจกต์เรา:* ตาราง `moderation.audit_logs` เก็บข้อมูลว่าใครเป็นคนสั่งลบ, เวลาใด, และระบุเหตุผลทางกฎหมายชัดเจน

### 12 · Data + Auth (s12: PostgreSQL 6 Schemas & Auth)

ระบบข้อมูลและยืนยันตัวตน:

ฐานข้อมูลใช้ PostgreSQL 16 ตัวเดียวแต่แยกเป็น 6 Schemas ตามขอบเขต Service เพื่อให้การทำธุรกรรมทางการเงินอยู่ใน ACID เดียวกันได้ และไม่มีคอลัมน์เก็บยอดเงิน Balance ดิบ แต่คำนวณจากผลรวมของ Ledger Entries แบบ Append-only เสมอ

ฝั่ง Auth ใช้ Better-Auth รองรับ Email และ Google Login โดยออก Session Cookie 7 วัน และแปลงเป็น Header ส่งต่อให้ Go ภายในคลัสเตอร์ครับ

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Database Schema Isolation**
>   - *คืออะไร:* การแบ่งห้องภายในฐานข้อมูลก้อนเดียวกันออกเป็นสัดส่วนตามขอบเขต Service
>   - *ในโปรเจกต์เรา:* มี 6 Schemas (`identity`, `catalog`, `commerce`, `reader`, `moderation`, `community`) ลดการผูกมัด (Loose Coupling) แต่ยังสามารถทำ ACID Transaction ร่วมกันได้
> - **Append-only Ledger**
>   - *คืออะไร:* สมุดบัญชีแยกประเภทที่อนุญาตเฉพาะการบันทึกเพิ่มแถวใหม่ (`INSERT`) ห้ามแก้ไข (`UPDATE`) หรือลบ (`DELETE`) เด็ดขาด
>   - *ในโปรเจกต์เรา:* ยอดเงินของผู้ใช้คำนวณจาก `SUM(amount)` ของประวัติทั้งหมด ป้องกันข้อผิดพลาดเงินล่องหน และตรวจสอบย้อนหลังทางบัญชีได้ 100%
> - **Header-based Identity Propagation**
>   - *คืออะไร:* การส่งต่อข้อมูลตัวตนผู้ใช้ผ่าน HTTP Header ภายในเครือข่ายเซิร์ฟเวอร์
>   - *ในโปรเจกต์เรา:* หน้าบ้านส่ง Cookie มาที่ Next.js แต่เมื่อคุยกับ Go จะส่งผ่าน Header `X-User-ID` และ `X-User-Role` ทำให้ Go ทำงานเบาและเร็ว ไม่ต้องแกะ Session ซ้ำ

### 14 · Architectural Trade-offs (s14: Trade-offs)

ข้อแลกเปลี่ยนในการออกแบบ:
- **ที่เลือกใช้**: R2 แม้ต้องดูแล 2 Cloud แต่ประหยัด Egress, Envoy Gateway ควบคุม Routing และ HPA ได้ดีแทน Nginx ที่ EOL, และ Postgres Flexible Server ปลอดภัยใน Private Subnet
- **ที่ตั้งใจตัดทิ้ง**: Redis เพราะ Postgres ทำงานได้เร็วระดับ 0.1ms ยังไม่มีคอขวด, Message Queue เพราะยังไม่มี Async Consumer จำเป็น, และ gRPC เพราะ REST เพียงพอและดีบักง่ายกว่า

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **ทำไมตัด Redis?**
>   - *คืออะไร:* In-Memory Caching Database ยอดนิยม
>   - *ในโปรเจกต์เรา:* จากการวัดผลจริง Query ใน PostgreSQL ใช้เวลาเพียง ~0.1ms หากใส่ Redis เพิ่มจะเพิ่มความซับซ้อนเรื่อง Cache Invalidation (แคชไม่อัปเดต) และเปลืองงบเซิร์ฟเวอร์โดยยังไม่มีคอขวด
> - **ทำไมตัด Message Queue (Kafka/RabbitMQ)?**
>   - *คืออะไร:* ระบบคิวส่งข้อความแบบ Asynchronous ระหว่างบริการ
>   - *ในโปรเจกต์เรา:* ยังไม่มีงานประมวลผลเบื้องหลังขนาดใหญ่ การยิง Synchronous HTTP ภายในคลัสเตอร์เดียวกันมีความเร็วระดับเสี้ยววินาทีและติดตามข้อผิดพลาดได้ง่ายกว่า
> - **ทำไมตัด gRPC แล้วเลือก REST?**
>   - *คืออะไร:* โพรโทคอลสื่อสารแบบ Binary ประสิทธิภาพสูงของ Google
>   - *ในโปรเจกต์เรา:* REST ผ่าน JSON เพียงพอกับปริมาณทราฟฟิก และมีข้อดีมหาศาลคือสามารถใช้เครื่องมือพื้นฐานอย่าง `curl` เข้าไปทดสอบและดีบักได้ทันที

### 15 · CI/CD Pipeline (s15: Pipeline)

สายพาน Azure DevOps ทำงาน 4 สเตจ ใช้เวลาราว 17 นาที:
1. `Lint`: ตรวจสอบโค้ดด้วย `go vet`
2. `Test`: ทดสอบบน Postgres จริง พร้อมประตูกั้น Coverage ≥80%
3. `Build`: สร้าง Docker Images 10 ตัวส่งเข้า Azure Container Registry (ACR)
4. `Deploy`: ทำ RollingUpdate ปัก SHA บน AKS แบบไร้ Downtime (เฉพาะ Master Branch)

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **CI/CD (Continuous Integration / Continuous Deployment)**
>   - *คืออะไร:* กระบวนการอัตโนมัติในการทดสอบ, รวมโค้ด, สร้างอิมเมจ และส่งขึ้นเซิร์ฟเวอร์จริงเมื่อมีการ Push โค้ด
>   - *ในโปรเจกต์เรา:* รันผ่าน Azure DevOps Pipelines แบ่งเป็น 4 ขั้นตอน ตรวจสอบโค้ดและส่งขึ้น AKS อัตโนมัติในเวลา ~17 นาที
> - **ACR (Azure Container Registry)**
>   - *คืออะไร:* คลังเก็บ Docker Images แบบส่วนตัวบนคลาวด์ Azure
>   - *ในโปรเจกต์เรา:* เก็บ Image ทั้ง 10 ตัว โดยคลัสเตอร์ AKS จะดึง Image ผ่านสิทธิ์ความปลอดภัยภายใน (AcrPull) โดยไม่ต้องต่อเน็ตนอก
> - **SHA Pinning**
>   - *คืออะไร:* การระบุเวอร์ชัน Image ด้วยรหัส Commit Hash ของ Git (เช่น `:338cb75`) แทนการใช้ป้ายกำกับกว้างๆ อย่าง `:latest`
>   - *ในโปรเจกต์เรา:* การันตีว่าโค้ดที่รันบน AKS คือโค้ดชุดเดียวกันกับที่ผ่านการทดสอบใน Pipeline แน่นอน และ Rollback ย้อนกลับได้แม่นยำ 100%

### 17 · K8s Load Test (s17: k6 Load Test)

ผลการทดสอบโหลดจริงด้วย k6:
เราจำลองผู้ใช้ 50 VUs ยิงเข้า API Gateway ต่อเนื่อง 5 นาที รวมกว่า 10,599 requests:
- Latency p95 อยู่ที่ 251ms (ผ่านเกณฑ์ที่ตั้งไว้ <300ms)
- Error rate เป็น 0.00%
- Kubernetes HPA ทำงานถูกต้อง โดยสั่งสเกล Reader Pod จาก 1 เป็น 2 Pods อัตโนมัติเมื่อ CPU เกิน 70%

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **k6 Load Testing**
>   - *คืออะไร:* เครื่องมือทดสอบประสิทธิภาพและการรับโหลดของเซิร์ฟเวอร์แบบโอเพนซอร์ส
>   - *ในโปรเจกต์เรา:* เขียนสคริปต์จำลองผู้ใช้งาน 50 คนเสมือน (VUs) ยิงเข้า `https://api.dootoon.store/read` ต่อเนื่อง 5 นาทีเพื่อทดสอบความเสถียรของคลัสเตอร์
> - **HPA (Horizontal Pod Autoscaler)**
>   - *คืออะไร:* ระบบขยายขนาดจำนวน Container (Pod) อัตโนมัติใน Kubernetes
>   - *ในโปรเจกต์เรา:* เมื่อมีคนเข้ามาอ่านพร้อมกันเยอะจน CPU ของ `reader pod` เกิน 70% Kubernetes จะสั่งเปิด Pod ใหม่เพิ่มจาก 1 ตัวเป็น 2–4 ตัวทันที เพื่อแบ่งเบาภาระ และยุบกลับเมื่อคนอ่านลดลง
> - **p95 Latency (95th Percentile Response Time)**
>   - *คืออะไร:* ค่าเวลาตอบสนองของผู้ใช้งาน 95% จากทั้งหมด (ตัดเคสช้าผิดปกติทิ้ง 5%)
>   - *ในโปรเจกต์เรา:* ทำเวลาได้ **251ms** ซึ่งเร็วกว่าเกณฑ์มาตรฐานของระบบเว็บ (<300ms) โดยมีอัตรา Error Rate เป็น **0.00%** จากหมื่นกว่า Request

ตัวเลขค่าใช้จ่ายจริงของระบบ:

> 💡 **Speaker Notes (คำอธิบายศัพท์เจาะลึก):**
> 
> - **Bandwidth / Egress Cost Comparison**
>   - *คืออะไร:* การเปรียบเทียบต้นทุนค่าส่งข้อมูลภาพการ์ตูนออกสู่อินเทอร์เน็ต
>   - *ในโปรเจกต์เรา:* หากมีคนอ่าน 100,000 ครั้ง/วัน ปริมาณภาพจะอยู่ที่ 45 Terabytes ต่อเดือน
>     - ถ้าวางบน **Azure Blob Storage**: โดนค่า Egress + Storage รวมราว **~$5,414 / เดือน** (~180,000 บาท)
>     - ถ้าย้ายมา **Cloudflare R2**: จ่ายเพียงค่าพื้นที่เก็บข้อมูล **~$11 / เดือน** (~380 บาท) เพราะค่า Egress ฟรี $0 ทำให้ประหยัดกว่าถึง 500 เท่า!
